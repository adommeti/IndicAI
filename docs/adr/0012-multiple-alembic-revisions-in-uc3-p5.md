# ADR 0012 — `uc3/P5` ships more than one alembic revision

- **Status:** Accepted
- **Date:** 2026-09-15
- **Owner:** `uc3/P5`
- **Relates to:** ADR 0010, ADR 0011; `.claude/rules/migrations.md`

## Context

`.claude/rules/migrations.md` opens with "one alembic revision per prompt at most". The rule
exists so that a prompt's schema change is a single reviewable, revertible unit.

`uc3/P5` cannot satisfy it as written. The prompt asks for two migrations in one sentence:
implement the E8 schema via alembic, **and** "create a dedicated DB role for the app with
INSERT/SELECT only ... and a migration that revokes UPDATE/DELETE". The chain anchor (ADR 0011)
adds a third table in the same prompt, and a hardening fix found in review adds a fourth
revision, because the same rule file forbids editing a revision that has left the branch.

## Decision

`uc3/P5` ships four revisions, linear, in this order:

- `0007_uc3_audit_chain` — the three chained tables.
- `0008_uc3_audit_role` — the `uc3_app` role, its grants, and the revokes against `PUBLIC`.
- `0009_uc3_chain_anchor` — `audit_chain_anchors`, the out-of-chain anchor the verify job writes.
- `0010_uc3_seq_generated_always` — `seq` from `GENERATED BY DEFAULT` to `GENERATED ALWAYS`
  (ADR 0010), so the INSERT-only role cannot plant its own sequence value.

They are kept separate rather than merged, because **schema, grants and hardening have different
rollback semantics**, and merging them makes the safe operation impossible without the dangerous
one:

- `0007.downgrade()` drops tables. It destroys the audit trail and must never be run against an
  environment holding data.
- `0008.downgrade()` revokes grants, deliberately leaves the role in place, and deliberately does
  not restore the `PUBLIC` write privileges it removed. It is cheap and non-destructive, and the
  grant model is the part most likely to need revision once a real deployment exists.
- `0009.downgrade()` drops one additive table and does not touch the chain.
- `0010.downgrade()` is a column attribute flip that loses nothing.

Merged into one revision, changing the grant model would mean editing a revision that also
contains a `drop_table`, and rolling the grants back would mean rolling the tables back. The
levels differ too: grants are cluster and role state, which may already exist on the target
(hence `0008`'s idempotence), while tables are schema state, which may not. `0010` could not
have been folded into `0007` under any reading — `0007` was already on the branch, and the rule
file's own "never edit a revision that exists on the base branch" is enforced by the repo hooks.

The rule still holds generally. The exception is narrow: a prompt may ship more than one revision
when **the prompt text itself asks for a separate migration**, when the revisions differ in
rollback semantics in the way above, or when a defect is found in a revision that has already
left the branch. Every other clause is unchanged — `NNNN_<uc>_<change>.py` naming, a linear
history with no branches, no edit to a shipped revision, idempotence wherever a revision touches
cluster-level objects, and `alembic upgrade head` plus `alembic check` green against a fresh
database in CI.

## Consequences

- **Positive:** the grant model can be tightened by a later revision without going anywhere near
  the revision that creates the tables — which is not hypothetical: `0008` needed one correction
  after review (an over-wide sequence grant), and `0009`'s docstring already names another grant
  that a later revision owes it.
- **Positive:** `0008` is safe to re-run on a cluster where `uc3_app` already exists: a
  re-deploy, a restored snapshot, or a shared cluster.
- **Negative:** the per-prompt bisect granularity the rule was protecting is gone.
  `alembic downgrade -1` no longer undoes "the P5 migration"; rolling P5 back is four steps, and
  the first of them is destructive.
- **Negative:** four revisions plus the model changes is more surface in one PR than the rule
  intends a reviewer to face at once, and the count is a hint that P5 is a large prompt rather
  than a licence to keep adding.
- **Follow-up required:** none. If shipping more than one revision per prompt becomes routine
  rather than exceptional, amend `.claude/rules/migrations.md` instead of accumulating ADRs
  against it.

## Evidence

- `prompts/uc3/P5.md` — asks for the E8 schema via alembic and, separately, "a migration that
  revokes UPDATE/DELETE".
- `platform/db/migrations/versions/0007_uc3_audit_chain.py`, `0008_uc3_audit_role.py`,
  `0009_uc3_chain_anchor.py`, `0010_uc3_seq_generated_always.py` — the four revisions and their
  asymmetric downgrades; each docstring states why it is its own revision.
- `.claude/rules/migrations.md` — the rule this deviates from; unedited.
- Verification: `uv run alembic upgrade head && uv run alembic check` green on a fresh database
  in CI's integration job (no pending autogenerate diff).
